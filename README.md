# a9量化-交易资管财富系统（以终为始）
## 项目核心定位
本项目源于“梦想中的交易资管财富系统”顶层愿景，目标是构建一套**机构级量化交易基座**，核心方向是从“现金流型资管系统（A类）”逐步演进为“中央银行式资管+无风险套利系统”，而“鲨鱼引擎+趋势引擎”仅作为第二类策略系统（B类）中的一组核心策略。第一阶段落地聚焦“资管双向非对称对冲”策略，基于Bitget交易所完成模块化、高稳定性、可扩展的底层架构搭建（Bitget仅作为第一个落地验证的交易所，后续可基于`ccxt_utils.py`的通用接口扩展至Binance、OKX等主流交易所），而非单一策略脚本的开发。

## 一、核心设计文档（演进逻辑：愿景→落地想法→需求分析→架构设计）
以下4份MD文档构成项目从“顶层愿景”到“可落地架构”的完整逻辑链，是理解项目核心思想的关键：

### 0. 梦想中的交易资管财富系统想法.md
- **定位**：项目的**顶层愿景文档**，定义了整个系统的终极目标、核心策略分类、交易哲学与分阶段实现路径。
- **核心内容**：
  - 交易哲学（系统设计的第一性原则）：
    1. 风险前置：任何收益都以风险可控为前提，监管层（`advanced_risk.py`）拥有绝对的指令否决权，是所有开发的核心准则；
    2. 分层盈利：通过“现金流型（压舱石）+方向性Alpha（收益增强）+凸性赌注（弹性补充）”的三层盈利结构，平衡收益稳定性与弹性；
    3. 模块化与抽象化：拒绝“一次性策略脚本”，以机构级模块化架构为核心，保证策略/交易所/风控规则的可替换性；
    4. 以终为始：所有第一阶段的开发都围绕终局系统的架构准则设计，避免重构成本，每一个模块都为后续三类策略融合预留扩展空间。
  - 终局系统核心策略分类（三类核心盈利模式）：
    1. **现金流型（Market Neutral / Carry / Spread）**：核心是创造稳定、低波动的现金流，聚焦市场中性、基差套利、持仓收益（Carry）、价差交易（Spread）等无风险/低风险策略，是整个资管系统的“压舱石”；
    2. **方向性 Alpha（趋势 / 主力 / 因子）**：通过捕捉市场趋势、主力资金动向、量化因子等获取超额收益，“鲨鱼引擎+趋势引擎”属于此类，是系统的“收益增强模块”；
    3. **凸性赌注（Convex Bet / Tail Risk / Lottery）**：针对黑天鹅事件、极端行情设计的高赔率策略，以小仓位博取极端收益，同时严格控制风险，是系统的“收益弹性补充模块”。
  - 系统分层：明确将整体系统拆分为两类核心模块——
    - A类：现金流型资管系统（核心是稳定现金流创造，聚焦上述第一类策略）；
    - B类：策略执行系统（承载第二类、第三类策略，鲨鱼引擎、趋势引擎属于第二类）。
  - 终极目标：将A类与B类系统融合，形成“中央银行式资管体系”（统一的风险监管、资金调配、策略执行）+“无风险套利闭环”。
  - 分阶段实现路径：
    - 第一阶段：落地B类系统中的“资管双向非对称对冲策略”（第二类方向性Alpha），验证核心架构；
    - 第二阶段：完善B类系统，新增第三类凸性赌注策略；
    - 第三阶段：落地A类现金流型资管系统，完成三类策略的融合与中央银行式监管体系搭建。

### 1. 资管双向原始想法（第一阶段落地，从梦想中的交易资管财富系统想法演化而来...）.md
- **定位**：项目**第一阶段落地的核心想法文档**，是从顶层愿景到具体策略的首次落地拆解。
- **核心内容**：
  - 落地聚焦：放弃终极愿景的全量落地，优先实现B类策略系统中“资管双向非对称对冲”这一核心策略（第二类方向性Alpha），作为整个基座的首个验证场景。
  - 核心逻辑：基于资管视角重构对冲策略，通过多空双向持仓的非对称配置（如仓位比例、止损/止盈幅度差异），既对冲市场波动风险，又捕捉趋势性收益，区别于传统单向策略。
  - 落地约束：明确第一阶段仅围绕Bitget交易所（首个落地交易所），完成“趋势识别→风险控制→订单执行”的核心链路，不涉及A类现金流系统和第三类凸性赌注策略。

### 2. 基于资管双向非对称对冲策略手册.md（第一阶段需求分析）
- **定位**：第一阶段落地的**结构化需求分析文档**，是开发的直接依据（将“原始想法”转化为可执行的功能/非功能需求）。
- **核心内容**：
  - 功能需求拆解：
    - 基础设施层：Bitget WS/REST API对接（稳定连接、消息解析、订单收发）；
    - 策略引擎层：趋势识别（趋势引擎）、交易决策（鲨鱼引擎）；
    - 风险监管层：仓位管控、非对称止损止盈、异常熔断；
    - 接口适配层：各模块间的标准化交互格式（信号、订单指令、状态反馈）。
  - 非功能需求：
    - 稳定性：WS断连自动重连、订单执行失败重试、核心状态不丢失；
    - 可扩展性：模块解耦，便于后续接入A类现金流系统或其他策略（如凸性赌注策略），且支持扩展至其他交易所；
    - 可维护性：参数配置化、日志标准化、核心逻辑注释清晰。
  - 策略细节量化：明确双向仓位比例（如多头30%/空头70%）、趋势信号触发阈值（如MACD金叉+波动率低于X）、止损幅度差异（多头2%/空头1.5%）等可落地参数。

### 3. 中央银行设计.md
- **定位**：项目的**当前核心架构设计文档**，是第一阶段及后续演进的唯一架构准则，系统的数据流设计、核心状态定义、模块交互规则均在此文档中持续更新。
- **核心内容**：
  - 架构核心理念：参考“中央银行”的“监管-执行-清算”逻辑，将系统拆分为三层——
    - 监管层（央行）：`advanced_risk.py`（风险控制、资金调配、阈值监管），所有交易指令必须经此层校验；
    - 执行层（商业银行）：`trend_engine.py`/`shark_engine.py`（策略决策、订单生成），仅负责输出指令，不直接对接交易所；
    - 基础设施层（清算系统）：`base_bitget_ws.py`/`ccxt_utils.py`/`bitget_ws_bridge.py`（交易所对接、指令转发、数据清算）。
  - 抽象化原则：定义通用接口（如策略引擎→风险层的指令接口、风险层→基础设施层的订单接口），保证模块解耦与替换性（如后续替换交易所、新增现金流/凸性赌注策略引擎）。
  - 状态管理：统一核心状态（仓位、订单、行情）的存储与同步规则，避免模块间状态不一致。
  - 数据流设计（核心更新内容）：
    1. 行情数据流：`base_bitget_ws.py`/`ccxt_utils.py` → `market_data_hub.py` → `trend_engine.py`/`shark_engine.py`；
    2. 指令数据流：`shark_engine.py` → `advanced_risk.py` → `tiny_oms.py` → `bitget_ws_bridge.py` → 交易所；
    3. 状态数据流：交易所 → `bitget_ws_bridge.py` → `data_synchronizer.py` → 全局状态池 → 各模块查询。
  - 核心状态定义（持续更新）：
    - 行情状态：K线、ticker、波动率等（存储于`market_data_hub.py`）；
    - 订单状态：订单ID、状态、成交金额等（存储于`tiny_oms.py`）；
    - 账户状态：仓位、资产、盈亏等（存储于`data_synchronizer.py`的全局状态池）；
    - 风险状态：单日回撤、仓位比例、订单失败率等（存储于`advanced_risk.py`）。

## 二、代码文件全解析（按“原型/基础设施/核心引擎/管控数据层/风险监管”分类）
### （一）早期原型代码（仅作对接参考，无模块化设计）
此类文件是项目初期为快速验证Bitget交易所对接流程开发的原型，**不纳入正式架构**，仅参考“WS对接、行情处理、仓位管理的技术细节”（如状态锁、异常处理）。

#### 1. martin.py
- **核心功能**：早期验证Bitget WS对接的最小原型，实现了“双向下单+简单平仓”的核心链路，无任何模块化拆分。
- **关键参考价值**：
  - 技术锁状态管理：解决WS推送行情与下单指令的并发竞态问题（如用`threading.Lock`保证订单指令串行执行）；
  - 基础WS异常处理：简单的断连重连逻辑、订单提交失败的重试机制；
  - 最小化对接示例：展示Bitget WS订阅行情、提交订单、查询账户的基础语法。
- **局限性**：
  - 耦合严重：交易所对接、策略逻辑、风险控制代码混写在同一文件；
  - 无扩展性：参数硬编码（如API Key、仓位比例），无法适配新策略；
  - 无监管层：订单直接发送至交易所，无风险校验环节。

#### 2. martin.json
- **核心功能**：`martin.py`的配套配置文件，存储交易所API密钥、策略基础参数（初始仓位、止损比例）、WS订阅频道。
- **定位**：原型阶段的简易配置，无分层、无校验，仅作“配置与代码分离”的参考示例。

#### 3. market_utils.py
- **核心功能**：原型阶段的**行情处理工具类**，为`martin.py`提供基础的行情数据处理能力。
- **关键参考价值**：
  - 基础行情解析：将Bitget WS返回的原始行情数据（如ticker、K线）转换为简单的结构化数据（如字典格式的K线信息）；
  - 简易指标计算：实现MA、MACD等基础趋势指标的极简计算逻辑，为后续`trend_engine.py`提供参考；
  - 行情缓存：实现本地短期行情缓存（如近100根K线），减少重复订阅/查询。
- **局限性**：
  - 无标准化接口：输出格式仅适配`martin.py`，无法直接复用至正式架构；
  - 无异常处理：行情解析失败直接抛出异常，无容错机制；
  - 指标计算简陋：无参数校验、无性能优化，仅满足原型需求。

#### 4. position_utils.py
- **核心功能**：原型阶段的**仓位管理工具类**，为`martin.py`提供基础的仓位计算、状态查询能力。
- **关键参考价值**：
  - 简易仓位计算：实现双向下单的仓位比例计算（如按账户资产的固定比例计算多空仓位）；
  - 仓位状态查询：查询Bitget账户的实时仓位，判断是否超仓、是否需要平仓；
  - 止损止盈计算：根据持仓均价计算简单的止损/止盈价格。
- **局限性**：
  - 无风险校验：仅计算仓位，无风险阈值管控逻辑；
  - 状态同步滞后：依赖轮询查询仓位，无实时同步机制；
  - 仅适配单一策略：仓位计算逻辑硬编码，无法适配非对称对冲需求。

### （二）交易所对接基础设施（稳定可用，架构核心底层）
此类文件是机构级基座的底层核心，负责与Bitget交易所的标准化对接，已验证稳定，是所有上层模块的基础（后续可扩展至其他交易所）。

#### 1. base_bitget_ws.py
- **定位**：Bitget WebSocket（WS）对接的**基础封装类**，是交易所交互的“底层核心”，已实现生产级稳定性。
- **核心功能**：
  - 连接管理：自动初始化WS连接、定时心跳保活（每30秒发送ping包）、断连后指数退避重连（避免频繁重试被风控）；
  - 消息处理：统一解析Bitget WS的行情（ticker/k线）、订单（成交/撤单）、账户（仓位/资产）消息，转换为标准化字典结构；
  - 订阅管理：封装“订阅/取消订阅”接口，支持批量订阅多个交易对/频道，记录订阅状态避免重复订阅；
  - 异常防护：捕获网络异常、消息解析错误、交易所风控提示，记录详细日志并保证连接不中断；
- **设计原则**：仅负责“底层WS通信”，不包含任何策略/风险逻辑，保证与上层模块的完全解耦。

#### 2. bitget_ws_bridge.py
- **定位**：基于`base_bitget_ws.py`的**桥接层**，是“基础设施层”与“执行层/监管层”的适配接口。
- **核心功能**：
  - 数据适配：将`base_bitget_ws.py`输出的原始行情数据，转换为策略引擎（trend_engine/shark_engine）可直接使用的格式（如聚合K线、趋势特征值）；
  - 指令转发：接收风险层校验通过的订单指令，转换为Bitget WS的订单格式并发送，同时接收执行结果并回传给风险层/策略引擎；
  - 状态同步：实时同步账户仓位、订单状态到全局状态池，供风险层/策略引擎查询；
- **核心价值**：屏蔽底层WS的细节，为上层模块提供“标准化的行情输入+订单输出”接口。

#### 3. ccxt_utils.py（重构版）
- **定位**：为适配“中央银行架构”重构的**CCXT工具类**，统一交易所API调用规范（支持多交易所扩展）。
- **重构背景**：早期原型的CCXT调用混乱，无统一异常处理，重构后适配机构级基座的模块化需求。
- **核心功能**：
  - 接口统一：封装“下单/撤单/查询账户/查询行情”等核心操作，提供标准化输入（如订单参数字典）和输出（如统一的订单状态枚举），屏蔽Bitget API的细节；
  - 多交易所预留：接口设计兼容CCXT支持的其他交易所，为后续扩展预留空间；
  - 异常处理：统一捕获CCXT的API异常（如网络错误、权限不足、订单超价），返回标准化错误码和提示信息；
  - 性能优化：实现行情数据本地缓存（如近1小时K线），减少重复API调用，降低交易所接口限流风险；
- **使用场景**：补充WS覆盖不到的场景（如批量查询历史订单、非实时资产清算），与`base_bitget_ws.py`形成“WS实时交互+REST批量查询”的完整对接体系。

### （三）核心管控与数据层（中央银行架构的中枢模块）
此类文件是“中央银行设计.md”中定义的核心管控组件，负责全局数据流、订单管理、主流程调度，是系统的“大脑中枢”，也是当前架构的核心新增模块。

#### 1. market_data_hub.py（行情数据枢纽）
- **定位**：系统的**行情数据统一枢纽**，是所有策略引擎的行情数据唯一来源。
- **核心功能**：
  - 数据聚合：接收`base_bitget_ws.py`的实时行情、`ccxt_utils.py`的历史行情，聚合为统一的行情数据集；
  - 数据分发：按策略引擎的订阅需求，将标准化行情数据推送至`trend_engine.py`/`shark_engine.py`，保证数据一致性；
  - 数据持久化：按需缓存/存储关键行情数据（如历史K线、趋势特征值），供策略回测/分析使用；
  - 多源校验：校验不同渠道（WS/REST）的行情数据一致性，避免因数据异常导致策略决策错误。

#### 2. data_synchronizer.py（数据同步器）
- **定位**：系统的**全局状态同步核心**，保证各模块间状态（仓位、订单、行情）的实时一致性。
- **核心功能**：
  - 状态同步：将`bitget_ws_bridge.py`获取的账户仓位、订单状态同步至全局状态池，供`advanced_risk.py`/`shark_engine.py`查询；
  - 增量更新：仅同步状态变化部分，减少模块间的数据传输开销；
  - 异常同步：当状态不一致时（如本地仓位与交易所仓位不符），自动触发校准逻辑（调用ccxt_utils.py查询交易所真实状态）；
  - 日志记录：记录所有状态同步记录，便于问题追溯。

#### 3. tiny_oms.py（轻量级订单管理系统）
- **定位**：系统的**订单全生命周期管理核心**，对应“中央银行架构”的“清算系统”环节。
- **核心功能**：
  - 订单创建：接收`advanced_risk.py`校验通过的指令，生成标准化订单对象（包含订单ID、方向、金额、止损止盈等）；
  - 订单跟踪：实时跟踪订单状态（已提交/部分成交/全部成交/已撤销/失败），同步至`data_synchronizer.py`；
  - 订单操作：封装订单撤销、修改（止损止盈点位）等操作，统一对接`bitget_ws_bridge.py`；
  - 订单风控：补充订单级的基础校验（如订单金额是否为交易所最小单位的整数倍），前置过滤无效订单。

#### 4. main_controller.py（主控制器）
- **定位**：系统的**全局主流程调度核心**，是“中央银行架构”的总入口。
- **核心功能**：
  - 模块初始化：按顺序初始化所有模块（基础设施层→数据层→监管层→执行层），保证模块启动顺序与依赖关系；
  - 流程调度：触发“行情接收→趋势识别→策略决策→风险校验→订单执行→状态同步”的全链路流程；
  - 异常兜底：当任一模块异常（如趋势引擎崩溃）时，触发兜底逻辑（暂停新指令、保留现有仓位），避免系统失控；
  - 配置加载：加载全局配置（如交易所参数、风险阈值、策略参数），分发至对应模块；
  - 启停控制：提供系统启动/暂停/停止的统一接口，便于运维与监控。

### （四）核心策略引擎（架构执行层，B类策略核心）
此类文件是“中央银行架构”的“执行层”，负责策略决策与订单指令生成，是第一阶段落地的核心。

#### 1. trend_engine.py（趋势引擎）
- **定位**：B类策略系统的**趋势识别核心**（第二类方向性Alpha），负责市场趋势的量化识别与信号生成。
- **核心功能**：
  - 趋势特征提取：基于行情数据（K线、波动率、成交量）计算核心指标（MACD、EMA、布林带、RSI），提取“趋势方向（多/空/震荡）”“趋势强度（0-1）”“趋势持续性（秒）”等特征；
  - 标准化信号输出：根据特征生成统一格式的趋势信号（如`{"direction": "long", "strength": 0.8, "confidence": 0.9, "timestamp": 1735689600}`）；
  - 非对称适配：支持针对多/空趋势设置不同的识别阈值（如多头趋势需EMA金叉+波动率<5%，空头趋势仅需EMA死叉），适配双向非对称对冲需求；
- **设计原则**：仅输出趋势信号，不参与交易决策，信号仅作为鲨鱼引擎的输入。

#### 2. shark_engine.py（鲨鱼引擎）
- **定位**：B类策略系统的**交易决策核心**（第二类方向性Alpha），是“执行层”的最终决策模块。
- **核心功能**：
  - 策略逻辑落地：基于趋势引擎的信号，结合“资管双向非对称对冲”规则，计算最优多空仓位比例、下单价格、止损/止盈点位；
  - 指令生成：输出标准化的订单指令（如`{"type": "open_position", "side": "long", "symbol": "BTC/USDT", "amount": 0.1, "stop_loss": 42000, "take_profit": 45000}`）；
  - 状态感知：读取全局状态池的仓位/订单状态，避免重复下单、超仓位下单；
  - 异常处理：趋势信号异常（如同时出现多/空信号）时，触发“保守策略”（维持当前仓位，不生成新指令）；
- **核心约束**：生成的所有指令必须先发送至风险层（`advanced_risk.py`）校验，通过后才能转发至交易所对接层。

### （五）风险监管核心（架构监管层，中央银行核心）
#### advanced_risk.py
- **定位**：“中央银行架构”的**监管层核心**，是所有交易指令的“最终把关人”，负责资金安全与风险控制。
- **核心功能**：
  - 仓位管控：限制单品种最大仓位（如BTC不超过账户资产的20%）、全账户多空总仓位比例（如多头≤60%、空头≤40%）；
  - 非对称止损止盈校验：验证鲨鱼引擎生成的止损/止盈点位是否符合非对称规则（如多头止损幅度≥2%，空头止损幅度≥1.5%），不符合则驳回指令；
  - 全局风险阈值监控：
    - 账户级：单日最大回撤≥5%时，暂停所有新指令；单日亏损≥10%时，强制平仓所有仓位；
    - 订单级：订单执行失败率≥30%时，暂停下单10分钟；大额订单（如金额≥10000 USDT）需校验盘口深度，滑点≥1%时拆分订单；
  - 指令校验与驳回：接收鲨鱼引擎的订单指令，逐项校验风险规则，通过则转发至桥接层，驳回则返回明确原因（如“多头仓位已达上限60%，当前仓位58%，无法新增2%仓位”）；
- **设计原则**：独立于策略引擎，拥有“一票否决权”，任何交易指令必须经此层校验，禁止绕过。

## 三、机构级基座开发实施路径（从头构建的核心步骤）
基于原型参考，按“模块化、抽象化、监管优先”的原则，从头构建机构级基座的步骤如下：

### 步骤1：完善基础设施层（交易所对接）
1. 以`base_bitget_ws.py`为基础，验证WS连接的稳定性（断连重连、心跳保活）；
2. 基于`ccxt_utils.py`重构REST API调用逻辑，完成“WS+REST”的完整对接（预留多交易所扩展接口）；
3. 开发`bitget_ws_bridge.py`的适配接口，输出标准化的行情/指令格式；
4. 参考`market_utils.py`的行情处理逻辑，重构标准化的行情解析/缓存模块（适配正式架构）；
5. 测试目标：交易所行情实时接收、订单正常提交/撤销、状态同步无延迟。

### 步骤2：搭建核心管控与数据层（中枢模块）
1. 开发`market_data_hub.py`的行情聚合/分发/持久化逻辑，保证策略引擎数据输入的一致性；
2. 开发`data_synchronizer.py`的全局状态同步与校准逻辑，保证本地状态与交易所一致；
3. 开发`tiny_oms.py`的订单全生命周期管理逻辑，统一订单操作接口；
4. 开发`main_controller.py`的模块初始化与流程调度逻辑，实现全链路自动化调度；
5. 测试目标：各模块启动顺序正确，行情/状态同步无延迟，订单跟踪准确。

### 步骤3：搭建风险监管层（中央银行核心）
1. 基于`advanced_risk.py`实现核心风险规则（仓位管控、止损校验、全局阈值）；
2. 参考`position_utils.py`的仓位计算逻辑，开发标准化的仓位管理接口（适配非对称对冲需求）；
3. 开发“指令校验接口”，定义鲨鱼引擎→风险层的指令格式；
4. 对接`data_synchronizer.py`的全局状态池，实现风险规则的实时校验；
5. 测试目标：违规指令（如超仓位下单）被正确驳回，触发阈值时自动暂停/平仓。

### 步骤4：开发策略执行层（B类策略核心）
1. 完善`trend_engine.py`的趋势识别逻辑，验证信号准确性；
2. 基于“资管双向非对称对冲”规则，开发`shark_engine.py`的决策逻辑；
3. 对接风险层校验接口，确保所有指令先校验后转发；
4. 测试目标：趋势信号正确转换为订单指令，违规指令被风险层拦截。

### 步骤5：全链路联调与优化
1. 打通“行情→趋势引擎→鲨鱼引擎→风险层→桥接层→交易所”的全链路；
2. 优化模块间的交互效率（如信号/指令的序列化方式）；
3. 补充日志、监控、配置管理等辅助功能；
4. 测试目标：全链路无异常，策略逻辑按预期执行，风险规则有效生效。

### 步骤6：分阶段扩展（向终局系统演进）
1. 第二阶段：基于现有架构，新增第三类“凸性赌注”策略引擎（如极端行情监测、高赔率下单逻辑）；
2. 第三阶段：开发A类“现金流型”策略模块（如基差套利、市场中性策略），完成三类策略的融合与中央银行式监管体系升级；
3. 长期扩展：基于`ccxt_utils.py`的通用接口，扩展至Binance、OKX等其他主流交易所。

## 四、核心总结
### 1. 文档核心逻辑
- 顶层愿景（梦想文档）：定义交易哲学+三类核心策略（现金流型/方向性Alpha/凸性赌注）+分阶段实现路径，是系统设计的根本准则；
- 落地路径：第一阶段仅实现B类系统中的“资管双向非对称对冲”（方向性Alpha），Bitget为首个落地交易所，后续逐步扩展至全品类策略与多交易所；
- 架构核心：《中央银行设计.md》是当前系统的唯一架构准则，数据流、状态定义、核心流程均在此持续更新，所有模块开发需严格遵循。

### 2. 代码分层核心
- 原型代码（martin.py/martin.json/market_utils.py/position_utils.py）：仅参考技术细节，不复用核心逻辑；
- 监管层（advanced_risk.py）：所有指令的最终把关人，核心是风险控制，拥有“一票否决权”；
- 执行层（trend_engine/shark_engine）：策略决策与指令生成，无直接交易所对接权限；
- 基础设施层（base_bitget_ws/bitget_ws_bridge/ccxt_utils）：标准化交易所对接，屏蔽底层细节，预留多交易所扩展；
- 管控数据层（market_data_hub/data_synchronizer/tiny_oms/main_controller）：系统中枢，负责全局数据流、订单管理、流程调度。

### 3. 开发关键原则
- 原型代码仅参考WS对接、行情/仓位处理的基础逻辑，正式架构需完全重构；
- 所有模块必须解耦，通过标准化接口交互，为后续新增三类策略、扩展多交易所预留空间；
- 风险监管层优先开发，且拥有指令的“一票否决权”，保证资金安全；
- 以终为始：第一阶段的每一个模块设计都需符合终局系统的架构准则，避免后期重构。
