a9quant-strategy: 机构级资管双向非对称对冲量化策略基座
本项目是基于 Bitget 交易所构建的机构级量化策略开发基座，核心目标是落地 “资管双向非对称对冲” 策略体系，从原始想法迭代到结构化设计，最终实现模块化、可扩展、高稳定性的量化交易系统。本文档将详细拆解项目的设计演进、文件功能与架构理念，为后续开发 / 大模型协作提供完整的参考依据。
一、需求与设计演进（核心文档）
项目的核心逻辑源于 3 份关键的设计文档，呈现 “原始想法→需求分析→架构设计” 的完整演进路径：
1. 1. 资管双向原始想法.md
定位：策略核心思路的起源文档，是整个项目的 “思想源头”。
核心内容：
提出 “资管双向对冲” 的核心构想：通过多空双向持仓的非对称配置，对冲市场波动风险，同时捕捉趋势性收益。
明确核心痛点：传统单向策略抗风险能力弱、非对称行情下收益效率低，需要从资管视角重构对冲逻辑。
初步勾勒策略的核心要素：双向仓位管理、非对称止损 / 止盈、趋势驱动的调仓逻辑。
2. 基于资管双向非对称对冲策略手册.md（需求分析）
定位：将原始想法落地为可执行的结构化需求文档，是开发的核心依据。
核心内容：
功能需求：拆解策略的核心模块（趋势识别、风险控制、交易所对接、指令执行等），明确各模块的输入 / 输出、交互逻辑。
非功能需求：定义系统的稳定性（WS 重连机制）、性能（行情处理延迟）、可扩展性（模块化架构）、安全性（风险阈值管控）要求。
策略细节：量化双向对冲的非对称参数（多空仓位比例、止损幅度差异）、趋势信号的触发条件、调仓频率等。
3. 中央银行设计.md3
定位：项目的架构设计文档，参考 “中央银行” 的监管 - 执行逻辑，构建机构级的模块化基座。
核心内容：
架构分层：基础设施层（交易所对接）、监管层（风险控制）、执行层（策略引擎）、配置层（参数管理）。
模块职责：明确趋势引擎、鲨鱼引擎、风险控制模块的边界与交互协议（如信号格式、指令规范）。
抽象原则：定义通用接口（如交易所适配接口、风险控制接口），保证模块解耦与可替换性。
二、代码文件详解
项目代码分为 “早期原型” 和 “机构级基座实现” 两类，以下逐一拆解每个文件的功能、定位与设计背景：
（一）早期原型代码（仅作对接参考，非模块化设计）
此类文件是项目初期为验证交易所对接流程开发的原型，未遵循模块化设计，仅用于参考 “交易所 WS 对接的技术细节”（如状态锁、重连逻辑），不纳入最终机构级基座的核心架构。
1. martin.py
核心功能：早期验证 Bitget 交易所 WS 对接的原型脚本，实现了最基础的双向交易逻辑（多空双向下单、简单平仓）。
关键参考价值：
包含技术锁状态管理：解决 WS 对接时的并发问题（如行情推送与下单指令的竞态），通过锁机制保证状态一致性。
基础的 WS 异常处理：简单的断连重连逻辑、消息解析错误捕获，为后续base_bitget_ws.py提供了对接思路。
局限性：代码耦合度高（交易所对接、策略逻辑、风险控制混写），无模块化拆分，参数硬编码多，仅用于学习对接流程，不适合扩展。
2. martin.json
核心功能：martin.py的配套配置文件，定义交易所接入参数（API Key/Secret）、策略基础参数（初始仓位、止损比例）、WS 订阅频道等。
定位：原型阶段的简易配置管理，未遵循机构级配置规范（如分层配置、参数校验），仅作参考。
（二）交易所对接核心（稳定可用，基座底层基础设施）
此类文件是机构级基座的底层核心，负责与 Bitget 交易所的 WS/REST API 对接，已验证稳定，是所有上层模块的基础。
1. base_bitget_ws.py
核心功能：Bitget WebSocket（WS）对接的基础封装类，是交易所交互的核心底层组件，已实现生产级稳定性。
关键实现：
WS 连接管理：自动连接、心跳保活（定时发送 ping 包）、断连自动重连（指数退避策略）。
消息处理：统一解析 Bitget WS 的行情 / 订单 / 账户消息格式，转换为标准化字典结构。
订阅管理：封装行情 / 订单流的订阅 / 取消接口，支持批量订阅。
异常处理：捕获网络异常、消息解析错误，记录日志并保证连接不中断。
设计原则：仅负责 “底层 WS 通信”，不包含任何策略逻辑，保证与上层模块的解耦。
2. bitget_ws_bridge.py
核心功能：基于base_bitget_ws.py的桥接层，为上层策略引擎适配 “中央银行” 架构的接口规范。
关键实现：
接口封装：将底层 WS 的原始消息（如行情 tick）转换为策略引擎可直接使用的标准化数据结构（如趋势引擎需要的 K 线聚合数据）。
指令转发：接收策略引擎的下单 / 平仓指令，转换为 Bitget API 的格式并通过 WS 发送，同时接收指令执行结果并回传给策略引擎。
状态同步：维护账户仓位、订单状态的实时同步，为风险控制模块提供实时数据。
（三）策略引擎核心（中央银行设计落地）
此类文件是 “中央银行” 架构中 “执行层” 的核心，实现策略的核心决策逻辑。
1. trend_engine.py（趋势引擎）
核心功能：实现 “中央银行” 设计中的趋势分析模块，负责市场趋势的识别、强度计算与信号生成。
关键实现：
趋势识别：基于均线、MACD、波动率等指标，识别市场的单边 / 震荡趋势，输出趋势方向（多 / 空 / 无）、趋势强度（0-1）。
信号生成：根据趋势特征，生成 “趋势确认”“趋势反转” 等标准化信号，传递给鲨鱼引擎作为交易决策依据。
参数适配：支持非对称趋势参数（如多头趋势的确认阈值高于空头），适配双向非对称对冲的需求。
2. shark_engine.py（鲨鱼引擎）
核心功能：策略的核心交易决策引擎，是 “中央银行” 架构的执行核心，基于趋势引擎的信号和风险控制参数生成交易指令。
关键实现：
非对称对冲逻辑：根据趋势信号，计算多空双向的最优仓位比例（非对称配置），生成下单 / 调仓 / 平仓指令。
指令校验：在发送指令前，先校验风险控制模块的阈值（如仓位是否超限、止损是否合理），保证指令合规。
状态管理：维护策略的运行状态（如当前持仓、已触发的信号），处理异常行情下的指令回滚（如订单失败时的仓位恢复）。
（四）风险控制核心（中央银行设计中的 “监管层”）
advanced_risk.py
核心功能：实现机构级的高级风险控制逻辑，是策略安全运行的核心保障，对应 “中央银行” 架构的 “监管层”。
关键实现：
仓位管控：限制单品种 / 全账户的最大仓位、多空仓位的比例上限。
止损止盈：实现非对称止损（如多头止损幅度 2%，空头止损幅度 1.5%）、动态止盈（随趋势强度调整）。
风险阈值：监控账户最大回撤、单日亏损上限、订单执行失败率，触发阈值时自动暂停策略或强制平仓。
流动性评估：结合 Bitget 的盘口深度，评估大额订单的滑点风险，调整下单节奏。
设计原则：所有策略指令必须经过风险控制模块的校验，只有通过校验的指令才能转发给交易所对接层，保证风险可控。
（五）接口封装重构（适配新架构）
ccxt_utils.py（重构版）
核心功能：为适配 “中央银行” 架构，重新封装的 CCXT 接口工具类，统一交易所 API 的调用规范。
重构背景：早期原型的接口调用混乱，重构后适配机构级基座的模块化需求，简化上层模块的交易所交互逻辑。
关键实现：
统一接口：封装下单、撤单、账户查询、行情获取等操作，提供标准化的输入 / 输出格式，屏蔽不同交易所的 API 差异（为后续扩展多交易所预留接口）。
异常处理：统一捕获 CCXT 的 API 异常（如网络错误、权限不足），返回标准化的错误码和提示信息。
性能优化：实现行情数据的本地缓存（如 K 线数据），减少重复的 API 调用，提升策略响应速度。
三、架构设计理念（机构级基座核心原则）
本项目的核心目标是构建 “机构级量化基座”，而非单一策略脚本，设计遵循以下核心原则：
模块化解耦：将交易所对接、风险控制、策略引擎拆分为独立模块，通过标准化接口交互，便于单独迭代、测试与替换。
抽象化通用：定义通用的接口规范（如策略引擎的信号格式、风险控制的校验接口），保证模块的可扩展性（如替换为其他交易所的 WS 对接层、其他类型的策略引擎）。
监管 - 执行分离：参考 “中央银行” 逻辑，风险控制模块作为 “监管层”，独立于策略引擎，所有交易指令必须经过监管层校验，保证资金安全。
四、开发与协作指引
1. 开发优先级
从底层到上层逐步实现：
第一步：基于base_bitget_ws.py和ccxt_utils.py完善交易所对接层（保证稳定）；
第二步：完成advanced_risk.py的风险控制逻辑（搭建监管层）；
第三步：迭代trend_engine.py和shark_engine.py的策略逻辑（落地执行层）；
第四步：通过bitget_ws_bridge.py整合各模块，适配 “中央银行” 架构。
2. 关键注意事项
WS 对接：重点关注base_bitget_ws.py的状态锁和重连逻辑，避免行情丢失或指令重复发送；
风险控制：所有交易指令必须经过advanced_risk.py的校验，禁止绕过监管层直接发送指令；
配置管理：参考martin.json的思路，重构分层配置体系（如全局配置、策略配置、风险配置），避免参数硬编码。
总结
核心关键点回顾
项目演进路径：资管双向原始想法.md（思路）→需求分析手册.md（需求）→中央银行设计.md3（架构）→ 代码实现（模块化基座）。
代码分层逻辑：基础设施层（Bitget WS 对接）→ 监管层（advanced_risk.py）→ 执行层（trend_engine/shark_engine）→ 桥接层（bitget_ws_bridge.py）。
原型与正式代码的区别：martin.py/martin.json 仅为早期对接参考，核心开发需基于重构后的 ccxt_utils、模块化的策略引擎和风险控制模块。
